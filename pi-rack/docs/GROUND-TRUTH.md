## 1. The first-boot mechanism changed, and most guidance is stale

**Raspberry Pi OS (trixie) configures first boot with cloud-init, seeded from
files on the FAT32 boot partition.** It is not `custom.toml`. It is not
`firstrun.sh` invoked from `cmdline.txt`. It is not `userconf.txt`. **(verified)**

How this was established, so it can be re-checked:

1. The official image index
   `https://downloads.raspberrypi.org/os_list_imagingutility_v4.json` declares
   `"init_format": "cloudinit-rpi"` on the current Raspberry Pi OS entries.
2. `2026-06-18-raspios-trixie-arm64-lite.img.xz` was downloaded
   (524,875,608 bytes), decompressed to 2,977,955,840 bytes, and its SHA-256
   computed: `e235fd24fc5f039c08daba7d3abc04aecc7313f979d16d2a3fdad29dd44c33a9`
   — **matching the `extract_sha256` the index publishes.**
3. The MBR was parsed: partition 1 is type `0x0c` (FAT32 LBA) at byte offset
   8,388,608, 537 MB, volume label `bootfs`; partition 2 is type `0x83` (Linux)
   at byte offset 545,259,520.
4. Listing partition 1 shows three files that do not belong to a firmware boot
   partition: **`user-data` (3277 bytes), `network-config` (1730 bytes),
   `meta-data` (921 bytes)**. Those are cloud-init NoCloud seed files.
5. Extracting `/etc/cloud/cloud.cfg.d/99_raspberry-pi.cfg` from partition 2
   confirms it outright:

   ```yaml
   datasource_list: [ NoCloud, None ]
   datasource:
     NoCloud:
       seedfrom: file:///boot/firmware
   ```

**Why this matters more than it looks:** almost every current tutorial, and the
first answer from most sources, describes the Bookworm-era `custom.toml`. A
wizard built on that writes a file the OS ignores, producing a Pi with no user,
no SSH key and no network — a node you have to physically retrieve. This single
fact is the difference between the wizard working and not.

### The exact seed contract

| File | Format | Purpose |
|---|---|---|
| `user-data` | `#cloud-config` YAML | users, SSH keys, hostname, packages, files, commands |
| `network-config` | netplan v2 YAML | static IP, gateway, DNS |
| `meta-data` | YAML | `instance_id`, `dsmode: local`, `local-hostname` |

All three go in the **root of the `bootfs` partition** — the drive letter Windows
mounts when you insert a freshly written card. No subdirectory.

### Details read out of the image that change how you write those files

From `/etc/cloud/cloud.cfg` **(verified)**:

- `system_info.default_user.name: pi`, `lock_passwd: True`, sudo
  `ALL=(ALL) NOPASSWD:ALL`, shell `/bin/bash`, distro class `raspberry-pi-os`.
  **The `pi` user is created *by cloud-init*, not baked into the image.** So a
  `users:` block that omits `- default` means `pi` is never created at all.
  That is how you remove the default account: by not asking for it.
- `disable_root: true`, `preserve_hostname: false` — so `hostname:` in
  `user-data` is honoured.
- `network.renderers: ['netplan', 'network-manager']` and
  `disable_fallback_netcfg: true`. NetworkManager is the activator, but the seed
  file is netplan v2 — you do not write `.nmconnection` files.
- `ntp_client: systemd-timesyncd`.
- Available modules include a Pi-specific `raspberry_pi` module, plus
  `write_files`, `users_groups`, `ssh`, `set_passwords`, `keyboard`, `locale`,
  `timezone`, `runcmd`, `package_update_upgrade_install`, `ansible`,
  `scripts_user`, `power_state_change`.

From `99_raspberry-pi.cfg` **(verified)**:

- `ssh_genkeytypes: []` and `ssh_deletekeys: false` — host keys are **not**
  generated by cloud-init. `regenerate_ssh_host_keys.service` does it on first
  boot. **Consequence: writing the same image to five cards does not give five
  Pis the same SSH host key.** That is a real worry with cloned images and it
  does not apply here.
- `emit_keys_to_console: false`, `no_ssh_fingerprints: true`.

From the shipped `meta-data` **(verified)** — the comment in the file says it
plainly:

> changing this will cause cloud-init to assume it is running on a "new"
> instance, and to go through first time setup again

The stock value is `instance_id: rpios-image`. The wizard replaces it with a
value derived from the node's plan entry, so **editing `fleet.toml` and
re-flashing genuinely re-provisions** instead of silently doing nothing.

From the shipped `network-config` **(verified)** — its own comments warn:

> if your boot sequence depends on active networking … you *must* mark at least
> one interface as required (`optional: false`) … particularly on faster boards,
> cloud-init will start attempting to use the network before it is ready

Every node in this plan installs packages on first boot, so `optional: false` is
mandatory, not stylistic.

### Stock `cmdline.txt` and `config.txt` in that image (verified)

```
console=serial0,115200 console=tty1 root=PARTUUID=041bba91-02 rootfstype=ext4 fsck.repair=yes rootwait resize
```

`config.txt` sets `arm_64bit=1`, `arm_boost=1`, `auto_initramfs=1`,
`camera_auto_detect=1`, `display_auto_detect=1`, `dtoverlay=vc4-kms-v3d`, and has

## 6. Corrections and additions — measured 2026-08-28 (later the same day)

### 6.1 The methodology error that caused most of this

The first scan tested a **fixed list of ports I had guessed at**. That is why it
concluded the NUC was running only Agent Deck and the Wyoming services. Scanning the
same hosts against a wider service-port list immediately found more. **A port scan only
ever tells you about the ports you asked about.** (verified)

### 6.2 The XiongMai DVR at `.49` is load-bearing infrastructure (verified)

`http://192.168.1.70:5000/api/stats` reports six cameras:

```
xmeye_1  xmeye_2  xmeye_3  xmeye_4  xmeye_5  tapo_outdoor
```

**Five of the six are `xmeye_*` — they are served by the XiongMai DVR.** So the DVR is
not a legacy box that can be unplugged; it is the encoder feeding most of the camera
estate, and Frigate, Alarmo, the driveway and the garage all depend on it.

**What this changes:**

- Any suggestion to "just remove it" is **wrong**. Strike it.
- Blocking its **outbound internet** on the router remains correct and safe — it does
  not touch reachability from `.70` on the LAN, which is same-subnet traffic.
- Any VLAN segmentation **must keep `.70` → `.49` RTSP reachable**, which means the
  camera VLAN needs the Frigate Pi with a leg in it, not a pure dead end.

### 7.4 Three Resolve APIs that change what is worth building (verified)

Read from `C:\ProgramData\Blackmagic Design\DaVinci Resolve\Support\Developer\Scripting\README.txt`:

- **`MediaPool:AutoSyncAudio([items], {settings})`** with
  `resolve.AUDIO_SYNC_WAVEFORM` or `AUDIO_SYNC_TIMECODE`. **Waveform-correlation
  multicam sync — the thing PluralEyes sells for ~$400 — is one documented call.** Any
  "sync the wedding automatically" tool is a scripting job, not a DSP project.
- **`AddMarker(frameId, color, name, note, duration, customData)`** on MediaPoolItem,
  Timeline *and* TimelineItem, with `GetMarkers()` and `DeleteMarkerByCustomData()`.
  The `customData` field is the important affordance: a tool can tag its own markers
  and later remove only its own.
- **`ImportTimelineFromFile`** (AAF/EDL/XML/FCPXML/DRT/ADL/OTIO),
  **`CreateTimelineFromClips(name, [{clipInfo}])`** with explicit frame positions, and
  **`Timeline:Export`** to EDL/FCPXML/OTIO/ALE/CSV.

And the limit that shapes everything: **there is no cross-project search API.**
`GetProjectListInCurrentFolder` lists names, but inspecting content requires
`LoadProject` — which resolve-sync's own rules forbid doing on a poll, because it yanks
the editor's session. Anything that searches across projects must build an index, not
query live.

Also present: `AnalyzeForIntellisearch(identifyFaces, isBetterMode)` — Resolve Studio
has AI face identification built in, which is prior art for any "find the family in the
archive" idea, though it too is per-project.

### 7.5 The DMX controller is more ready than expected (verified)

`N:\DMX Controller\main.py` is FastAPI with a WebSocket and, notably, a set of plain
`GET` endpoints clearly built for a Stream Deck:

```
/sd/blackout      /sd/full      /sd/preset/{preset_id}
/sd/scene/{name}  /sd/channel/{universe}/{channel}/{value}
```

Scene recall is therefore a URL. Home Assistant can drive the lighting rig with a

Combined with the existing `pi_install.sh`, putting this on a Pi is a deployment, not
a project.

### 7.6 Dental Story, on disk (verified)
